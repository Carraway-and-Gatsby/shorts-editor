# 9. 로드맵 (Roadmap)

[2.3 릴리스 단계별 범위](02-feature-definition.md#23-릴리스-단계별-범위)를 실행 가능한 마일스톤으로 구체화한다.
각 마일스톤은 **동작하는 수직 슬라이스**를 목표로 한다 (레이어별 완성이 아니라 끝에서 끝까지 이어지는 기능 단위).

## M0 — 프로젝트 골격

- [ ] 모노레포 구조 셋업 (`apps/`, `workers/`, `packages/`) + Docker Compose
- [ ] CI: 린트, 타입체크, 테스트 파이프라인
- [ ] `packages/shared`: composition 스키마(JSON Schema + 타입), 잡 상태 상수
- [ ] 큐/스토리지 추상화 인터페이스와 로컬 구현체

**완료 기준**: `docker compose up`으로 전 서비스가 뜨고 헬스체크가 통과한다.

## M1 — 파이프라인 뼈대 (변환만 하는 통짜 흐름)

- [ ] 업로드 API (청크 업로드, 잡 생성) — F-01, F-02 일부
- [ ] Ingest 워커: 검증 + 프록시 + 썸네일
- [ ] Render 워커: **컷/자막 없이** 9:16 pad 모드 변환만 수행 — F-13 pad
- [ ] 잡 상태 머신 + SSE 진행률 — F-40
- [ ] 최소 웹 UI: 업로드 → 진행률 → 미리보기 → 다운로드 — F-20, F-30

**완료 기준**: 어떤 지원 포맷 영상이든 업로드하면 9:16 MP4가 나온다. (UC-1의 골격)

## M2 — 자동 편집 두뇌 (MVP 완성)

- [ ] Analyze 워커: 샷 감지 + 신호 점수 — F-10
- [ ] Analyze 워커: STT + 무음 감지 — F-11
- [ ] Compose: 하이라이트 선택 알고리즘 — F-12
- [ ] 피사체 추적 크롭 (`track` 모드) — F-13 완성
- [ ] 자막 생성·리매핑·번인 — F-14
- [ ] 평가셋 구축: 샘플 영상 20개 + 기대 결과 라벨, 점수 가중치 튜닝 루프

**완료 기준**: [UC-1](03-functional-spec.md#31-대표-유스케이스)(완전 자동 생성)과 UC-3(무음 영상)이 통과한다. → **MVP(v0) 릴리스**

## M3 — 보정과 스타일 (v1)

- [ ] 생성 옵션 UI — F-03
- [ ] BGM 라이브러리 + 믹싱/라우드니스 — F-15
- [ ] 프리셋 4종 (`clean`/`bold`/`vlog`/`promo`) — F-16
- [ ] 컷 보정 타임라인 UI — F-21
- [ ] 자막 편집 UI — F-22
- [ ] 재렌더링(리비전) — F-24
- [ ] 잡 이력 + 보관 정책 배치 — F-41

**완료 기준**: UC-2(자막 수정 → 재렌더)가 통과한다. → **v1 릴리스**

## M4 — 계정과 확장 (v2)

- [ ] 사용자 계정, 익명 이력 병합 — F-42
- [ ] 스타일 개별 교체 — F-23
- [ ] S3 스토리지/서명 CDN 전환, 워커 스케일아웃
- [ ] 금칙어 마스킹(F-14-R3), 클라우드 STT 옵션 재검토(ADR-3)

## M5+ — 게시와 협업 (v3+)

- [ ] 플랫폼 직접 업로드 (YouTube Data API 우선) — F-31
- [ ] 멀티 클립 프로젝트
- [ ] 팀/브랜드 프리셋 공유

## 리스크와 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 하이라이트 품질이 기대 이하 | 제품 핵심 가치 훼손 | M2에서 평가셋 기반 튜닝을 기능 구현과 동급 작업으로 취급. 자동 결과가 나빠도 F-21 보정으로 탈출구 확보 |
| 피사체 추적 크롭의 흔들림/오추적 | 시청 불가 수준의 결과물 | 스무딩 규칙(F-13-R2) + 신뢰도 낮으면 pad 모드 자동 폴백 |
| CPU 렌더링 처리 시간 초과 | NFR-10 미달 | 프록시 기반 병렬 처리, NVENC 지원, 워커 수평 확장 준비 |
| STT 오인식(한국어 고유명사 등) | 자막 품질 저하 | 자막 편집(F-22)으로 보완, stt_corrections 수집으로 개선 우선순위 판단 |
| BGM/폰트 라이선스 | 법적 리스크 | NFR-36/NFR-62: 등록 시 라이선스 검증 절차 필수화 |

- 본 명세의 변경은 PR로 제안하고, 결정 사항은 해당 문서에 반영한다.
- 구현 중 명세와 어긋나는 결정이 필요하면 **문서를 먼저 수정**한 뒤 코드를 변경한다.
- 아키텍처 결정은 [5.5 ADR 요약](05-architecture.md#55-주요-기술-결정-기록-adr-요약)에 항목을 추가한다.
